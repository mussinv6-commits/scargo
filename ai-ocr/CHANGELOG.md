## gate_api.py DB 드라이버를 psycopg2 → pg8000으로 교체 (2026-09-30)

### 배경
백엔드(scargo) 코드를 게이트 마스터 구조로 다 고치고 Spring Boot 재시작까지
정상 확인한 뒤, `gate_api.py`를 실제로 띄워보니 로그인(`scargo 로그인 성공:
admin`)까지는 잘 됐는데, 그다음 trucks 조회용 DB 연결에서
`psycopg2.connect()`가 `UnicodeDecodeError: 'utf-8' codec can't decode byte
0xb8...`로 실패함. 콘솔 코드페이지를 UTF-8로 바꾸거나(`chcp 65001`)
`PYTHONUTF8=1`을 줘도 동일하게 재현됨 - psycopg2의 C 확장(libpq)이 한국어
Windows 로케일(CP949)에서 겪는 것으로 알려진 문제로 파이썬/콘솔 설정으로는
못 고침. 참고로 완전히 동일한 계정/DB로 scargo(Spring Boot/JDBC)는 이미 정상
접속되는 것을 확인했으므로 PostgreSQL 서버나 계정 자체 문제는 아님.

### 변경
- `gate_api.py`의 `get_db_connection()`을 `psycopg2` 대신 C 확장이 없는 순수
  파이썬 드라이버 `pg8000`(`pg8000.dbapi`)으로 교체. DBAPI2 호환이라
  `cur.execute(...)`/`cur.fetchone()`/`conn.commit()` 등 나머지 조회 코드는
  전혀 수정 없이 그대로 재사용됨.
- 실행 준비 안내(모듈 docstring)의 `pip install ...` 목록에서
  `psycopg2-binary`를 `pg8000`으로 교체.

## scargo gate_logs 스키마 개편(게이트 마스터 테이블 도입) 대응 - 백엔드/gate_api.py 동시 수정 (2026-09-30)

### 배경
사용자가 게이트 마스터 테이블(`gates`)을 추가한 최신 `schema.sql`을 이미 실제
PostgreSQL에 반영해둔 상태였음. 이 스키마에서는 `gate_logs.gate_name`/
`gate_type` 컬럼이 사라지고, 대신 `gate_logs.gate_id`(INT, FK)가 새로 생긴
`gates` 마스터 테이블(게이트 코드/이름/구분/위경도/설명 등을 담는 테이블,
ABC야드/I야드/H야드/DEFG야드 4개 게이트 씨드 포함)을 참조하는 구조로 바뀌어
있었음. 그런데 scargo 백엔드(`GateLog` 엔티티 등)와 `gate_api.py`는 계속
옛 설계(`gate_name`/`gate_type`을 문자열로 직접 저장) 기준으로 작성돼 있어서,
Vue 프론트가 `GET /api/v1/gate-logs`를 폴링할 때마다 Hibernate가
`오류: gl1_0.gate_name 칼럼 없음`(PSQLException, SQLState 42703) 에러를
반복적으로 던지고 있었음 - 사용자가 "칼럼있어"라고 반박한 것도 사실은 맞는
말이었음(다만 Hibernate가 찾던 `gate_name`이 아니라 `gate_id`가 있었던 것).
→ 두 방향(스키마를 옛날 구조로 되돌리기 / 코드를 새 게이트 마스터 구조에 맞게
업데이트하기) 중 사용자가 "새 게이트 마스터 구조로 코드 업데이트"를 선택함.

### scargo 백엔드 변경
- **신규**: `entity/Gate.java` - `gates` 테이블 매핑 엔티티(gateId, gateCode,
  gateName, gateType, latitude, longitude, locationDescription, isActive,
  createdAt).
- **신규**: `repository/GateRepository.java` - `findByGateCode(String)` 제공.
  클라이언트(gate_api.py 등)가 DB가 자동 생성하는 숫자 `gate_id` 대신 고정된
  `gate_code`(예: `Gate-ABC-01`)로 게이트를 지정할 수 있게 함(schema.sql이
  재실행돼서 SERIAL 값이 바뀌어도 코드는 안전).
- `entity/GateLog.java`: `gateName`/`gateType` String 필드를 제거하고
  `@ManyToOne` `Gate gate`(`@JoinColumn(name="gate_id")`)로 교체. `update()`는
  게이트 재배정을 더 이상 처리하지 않음(DB 조회가 필요해서 서비스로 이동).
- `dto/GateLogCreateRequest.java` / `GateLogUpdateRequest.java`:
  `gateName`/`gateType` 필드를 제거하고 `gateCode`(문자열) 필드로 교체.
- `dto/GateLogResponse.java`: `gateId`/`gateCode`/`gateName`/`gateType`을
  연결된 `Gate` 엔티티에서 꺼내 그대로 평탄화해서 응답에 포함 - Vue
  `GateDemo.vue`가 이미 `log.gateName`/`log.gateType`을 테이블에 그대로 쓰고
  있어서(수정 불필요), 프론트 호환을 위해 응답 모양은 그대로 유지함.
- `repository/GateLogRepository.java`: `findByGateType(...)` /
  `findByGateNameAndPassAtBetween(...)` / `findByGateTypeAndPassAtBetween(...)`를
  Spring Data JPA 중첩 프로퍼티 탐색을 이용해 `findByGate_GateType(...)` /
  `findByGate_GateNameAndPassAtBetween(...)` /
  `findByGate_GateTypeAndPassAtBetween(...)`로 교체(Gate 조인 쿼리 자동 생성).
- `service/GateLogService.java`: `GateRepository` 주입. 생성/수정 시
  `gateCode`로 `Gate`를 조회해서 없으면 `IllegalArgumentException`, 있으면
  `GateLog.gate`에 설정.

### gate_api.py / gate_watch_service.py 변경
- `gate_api.py`: `DEFAULT_GATE_NAME`/`DEFAULT_GATE_TYPE` 상수를
  `DEFAULT_GATE_CODE = "Gate-ABC-01"` 하나로 교체, `/scan`이 scargo에 보내는
  payload도 `"gateName"/"gateType"` → `"gateCode"`로 교체.
- `gate_watch_service.py`: CLI 인자 `--gate-name`/`--gate-type`을
  `--gate-code`(기본값 `Gate-ABC-01`) 하나로 교체, `process_one_file()` 시그니처
  및 payload도 동일하게 교체.
- Vue 측(`GateDemo.vue`)은 변경 없음 - 게이트로그 생성은 항상 gate_api.py를
  통해서만 일어나고, Vue는 조회(GET)만 하는데 응답 모양이 그대로 유지되므로
  수정 불필요함을 확인함.

### 다음 필요 작업 (사용자 확인 대기)
- scargo 백엔드를 재시작해서 위 변경사항을 반영해야 함(핫리로드 아님).
  재시작 시 `AdminInitializer`가 `accounts` 테이블이 비어있으면 admin 계정도
  같이 재생성하므로, 이전에 진단된 "존재하지 않는 아이디입니다" 로그인 실패도
  같은 재시작으로 같이 해결될 가능성이 높음.
- 재시작 후 `POST /api/v1/gate-logs`(gate_api.py가 호출)가 `gateCode:
  "Gate-ABC-01"`로 정상적으로 게이트 로그를 저장하는지, 그리고 Vue의
  `GET /api/v1/gate-logs` 폴링에서 더 이상 `gate_name 칼럼 없음` 에러가 나지
  않는지 확인 필요.

## gate_watch_service.py 랜덤 1장씩 처리로 변경 + gate_api.py(FastAPI, HTTP 트리거) 신규 추가 (2026-09-30)

   트리거되게 함(폴더 폴링 대신 요청 1번당 무작위 사진 1장 처리 - 발표 중 버튼을

   게이트인 버튼 onClick에서 이 엔드포인트를 호출하면 됨.
3. 등록차량(번호판+차종) 매칭: 처음엔 새 테이블(gate_registered_vehicles)을 만들
   계획이었으나, scargo 백엔드의 `Truck.java`/`schema.sql`을 직접 확인한 결과

   존재하고, `GateLog.java`의 `actualVehicleNo` 필드도 이미 "매칭된 차량 번호판

   `GateLogCreateRequest.actualVehicleNo` 필드에 그대로 채워 보냄(스키마/DTO

## gate_watch_service.py 실행파일(exe)화 준비 - frozen 경로 대응 + GateWatchService.spec 추가 (2026-09-29)

### 배경
사용자: "실행파일을 따로만들고 폴더 설정도 해야되네" - gate_watch_service.py를
CargoScan.exe처럼 배포 가능한 실행파일로 만들어야 함을 지적.

### 발견한 문제
`gate_watch_service.py`가 import하는 `batch_test_images.py`는 `APP_DIR = Path(__file__)
.resolve().parent`를 그대로 쓰고 있었음 - PyInstaller onedir exe로 빌드되면
`__file__`이 exe가 있는 실제 폴더가 아니라 그 안의 `_internal` 폴더를 가리켜서
(plate_detector_gui.py의 `_exe_dir()` 주석에 이미 기록된 것과 동일한 문제),
`ocr_model_attn/`, `runs/detect/` 같은 모델 경로를 exe 배포 시 못 찾게 됨.
gate_watch_service.py 자신의 APP_DIR(감시 폴더/로그 파일 위치 기준)도 동일한 문제.

### 조치
1. `batch_test_images.py`, `gate_watch_service.py` 둘 다 `plate_detector_gui.py`의
   `_exe_dir()`와 동일한 함수를 추가해서 `APP_DIR`을 여기 기준으로 바꿈(frozen이면
   `sys.executable` 기준, 아니면 기존과 동일하게 `__file__` 기준 - 스크립트로
   실행할 때는 동작 변화 없음).

### 새로 만든 것: gate_watch_service.py
`gate_live_demo.py`는 그대로 남겨둠(발표 녹화용으로 계속 사용 가능) - 완전히

데모 대비 추가/변경된 것:
- **폴더 폴링**: 지정 폴더(기본 `게이트_수신함`, --watch-dir로 변경 가능)를
  poll-interval(기본 2초)마다 훑어봄. 카메라가 파일을 쓰는 도중 잡지 않도록,
  파일 크기가 0.3초 간격으로 안정적일 때만 처리 시작.
- **처리 후 이동**: 성공/판독불가는 `processed/`로, 이미지 자체가 깨졌거나
  예외가 난 경우는 `failed/`로 이동 - 중복 재처리 방지 + 나중에 `failed/`만
  확인하면 진짜 문제였던 사진만 모아서 볼 수 있음. 같은 이름 파일이 이미
  대상 폴더에 있으면 타임스탬프를 붙여 안 덮어씀.
- **계정 환경변수화**: `get_credentials()`가 GATE_API_ID/GATE_API_PW를 못 찾으면
  바로 SystemExit - 평문 기본값으로 조용히 안 넘어감.
- **재시도**: 서비스 시작 시 백엔드 연결 실패는 죽지 않고 5초마다 재시도(상시

  1회 재로그인 후 재시도.
- **logging 모듈**: print 대신 콘솔+`gate_watch_service.log` 파일에 타임스탬프
  찍힌 로그를 같이 남김.
- **Ctrl+C 정상 종료**: 종료 시 처리 건수 요약(인식성공/판독불가/이미지오류/
  DB저장실패) 출력.

  "자신만만하게" 틀린 답을 냄. 즉 confidence 비교나 다수결 방식 앙상블을
  쓰면 최선의 경우에도 14건을 구하면서 최악의 경우 45건 이상을 새로 틀리게
  만들 위험이 있어 순손실 가능성이 훨씬 큼.
- BiLSTM만정답 14건을 개별로 봐도, BiLSTM이 어텐션보다 confidence가 높은
  경우는 14건 중 8건뿐(나머지 6건은 어텐션이 confidence는 더 높으면서 틀림) -
  "confidence 높은 쪽 채택" 같은 단순 규칙으로는 애초에 14건 중 절반 정도만
  구제 가능하고, 그마저도 99건 쪽 리스크(45건 오염)를 감수해야 함.
- 이건 2026-09-29 앞선 항목의 "EasyOCR 상시대조 다수결 실패"(정답 73건을
  오답으로 뒤집음)와 정확히 같은 실패 패턴 - 서로 다른 모델의 confidence는
  같은 기준으로 비교 불가능함이 재확인됨.
- **결론: 앙상블 보류.** 두 모델을 합쳐서 얻을 수 있는 최대 이득(14건,
  전체의 1.8%)이 확인된 리스크(최소 45건 오염 가능성)보다 훨씬 작아서,
  추가 개발 없이 여기서 중단. `diagnose_ensemble.py`는 진단 전용이라
  프로덕션 코드(`plate_ocr_crnn_attn.py`, `batch_test_images.py`)는 그대로
  둠 - 나중에 두 모델의 confidence를 서로 비교 가능하게 보정(calibration)하는
  방법이 생기면 그때 재검토 가능.

  대전↔대구, 울산↔부산 등 - 둘 다 유효한 지역명이라 문법 검사로 못 걸러짐),
  사자바아보모고노로배 유사문자 혼동 6건(학습 시 가중치 1.5배 줬는데도 여전히
  샘), 숫자 하나 누락/중복(CTC 붕괴 추정) 3건(예: 경남99사8551->경남99사851,
  8자리로 줄어 문법 자체를 어김), 나머지 4건은 산발적. 판독불가 68건은 전부
  engine="easyocr"/"easyocr_alt"(0건이 crnn) - CRNN이 판독불가로 빠지는 경우는
  없고, 폴백이 발동된 뒤 EasyOCR 자체가 애매해서 못 읽는 쪽에 전부 몰림.
- **검토한 대안과 선택**: (A) 지역명 혼동쌍만 좁게 EasyOCR 강제 대조(속도 손해
  최소, 지역명 8건 위주 커버) vs (B) 확신도 통과 여부와 상관없이 EasyOCR(본선)을
  항상 한 번 대조(속도 손해 있지만 21건 전체가 대상) - 사용자가 "정밀한 쪽"(B)을
  선택함, 속도 손해 감수(2026-09-29).
- **조치 (batch_test_images.py, ocr_plate())**: 기존엔 CRNN 확신도가 임계값(0.5)
  이상이면 EasyOCR을 아예 안 돌리고 즉시 반환했는데, 이제 확신도 통과해도
  EasyOCR(본선)을 항상 한 번 같이 돌려서 대조함. 판단 순서:
  1) CRNN 결과에 번호판 문법 검사(_is_valid_plate_format)를 새로 추가 - 어기면
     (숫자 누락/중복 케이스) 기존 폴백 로직으로 넘어가 EasyOCR 의견을 채택.
  2) 문법은 맞는데 EasyOCR(본선)과 내용이 다르면(지역명/유사문자 혼동 의심)
     EasyOCR_alt까지 추가로 한 번 더 돌려서 3자(CRNN/본선/alt) 다수결 시도 -
     독립된 두 EasyOCR 판독이 서로 일치하면서 CRNN과는 다를 때만(2/3 이상)
     뒤집음. 다수가 안 갈리면(3자 전부 다르거나 CRNN이 이미 다수) CRNN을 그대로
     유지 - 애매하면 안 뒤집는 게 안전하다는 기존 원칙 유지.
  3) EasyOCR(본선)이 문법에 안 맞거나 CRNN과 일치하면 alt도 안 부르고 즉시 CRNN
     채택 - 매 이미지 EasyOCR 본선은 항상 돌지만 alt는 실제 disagreement가 있을
     때만 돎(무조건 2배가 아니라 상황에 따른 추가 호출).
  뒤집힐 때는 engine 태그를 "easyocr"/"easyocr_alt"로 남겨서 main()의 기존
  grammar 필터가 한 번 더 검증하게 함(이중 안전장치).
- **검증**: 실제 CRNN/EasyOCR 모델 없이는(클라우드 환경에 torch/easyocr 없음)

  **실제 정확도 개선 여부와 부작용(속도 저하 정도, 새로 생기는 오답)은 사용자가

## 2줄 번호판 확신도 진단 (2026-09-28) - 원인은 확인됨(T-정규화 안 된 beam-search 확신도), 그러나 ❌ 실측 결과 유의미한 개선 없음, 코드 동작 변경 안 함
- **배경**: unwrap_two_line 재작성으로 2줄 정확도가 77.3%->84.2%까지 올랐지만
  (767장 기준 전체 86.7%), 남은 2줄 실패 48건(판독불가 38 + 오답 10)을 분석함.
  ocr_plate() docstring에 이미 남겨져 있던 단서 - "2줄은 CRNN 자체 정확도(임계값
  통과 시 96.8%)는 1줄(96.9%)과 거의 같은데, 확신도 미달로 폴백되는 비율이 1줄
  (7.6%)보다 훨씬 높다(27%)" - 를 실제로 추적함.
- **확인 1 (CSV 재분석)**: 실패 48건 중 CRNN 원본 추측(임계값 무관)이 실제로
  정답과 정확히 일치하는데도 확신도(0.16~0.39)가 0.5를 못 넘어서 버려진 사례가
  다수 확인됨(예: 대전89아6993, 부산80러4819, 충북85아6218, 경기91아9214).
  단, "임계값을 그냥 낮추면 되지 않을까"는 안 됨 - 같은 방식으로 시뮬레이션해보면
  이미 맞았던 3건이 깨지고, 진짜 판독불가였어야 할 56건이 "그럴듯하지만 틀린
  답"으로 둔갑함(v3.14 이전 threshold 실험 때와 동일한 결론 재확인 - 조준을
  못 하는 둔탁한 조정은 항상 역효과).
- **확인 2 (실측 15장 표본, 라벨 파일로 크롭 재현)**: 전처리 캔버스의 "실제 내용
  폭"(흰 여백 제외)을 재보니, 1줄 표본 6장은 150~171px(추정 타임스텝 T≈37~42)인데
  반해 2줄 표본 9장(정답 5장 + 임계값 미달 판독불가 4장 전부 포함)은 예외 없이
  캔버스 상한(320px, T=80)에 도달함 - unwrap_two_line이 위/아래 두 줄을 옆으로
  이어붙이면서 폭이 1줄보다 구조적으로 훨씬 넓어지기 때문.
- **가설**: `ctc_beam_search_decode`가 반환하는 확신도(p_b+p_nb)는 CTC forward
  알고리즘으로 T 타임스텝 전체에 걸쳐 확률을 곱해나간 "정규화 안 된 결합확률"이라,
  T가 클수록(2줄처럼) 같은 글자 정확도라도 값이 기하급수적으로 더 작게 나옴 -
  즉 threshold=0.5가 사실상 2줄에만 훨씬 가혹하게 적용되고 있었을 가능성이 높음.
- **조치 (진단 전용, 실제 동작 변경 없음)**: `plate_ocr_crnn_attn.py`에
  `estimate_timesteps()`(모델 재실행 없이 전처리 캔버스 크기만으로 T 추정)와
  `normalized_confidence()`(conf ** (1/T) 기하평균 정규화) 두 순수 함수를
  추가함 - `ocr_plate()`/`CRNNRecognizer.recognize()`의 실제 채택 로직은 전혀
  안 건드림. `batch_test_images.py`가 이미 계산돼 있는 crnn_raw_conf를 이
  함수로 정규화해서 CSV에 새 진단 컬럼("CTC타임스텝수T(진단용)",
  "T정규화확신도(진단용,임계값미적용)")으로만 남기게 함.
- **실측 검증 (767장 재실행 후 CSV 분석)**: 가설(원인) 자체는 767장 전체 기준으로
  강하게 재확인됨 - 1줄 T 중앙값 39(최대 71) vs 2줄 T 중앙값 80(304장 중 95.1%가
  캔버스 상한 T=80에 도달). 그런데 T정규화확신도로 diagnose_crnn_threshold.py와
  같은 방식으로 여러 임계값(0.90~0.995)을 시뮬레이션한 결과, "원래 채택 기준과
  동등한" 임계값(~0.99)에서는 결과가 원래(665/28/74)와 완전히 동일했고, 임계값을
  낮춰서 더 많은 2줄 저확신도 사례를 구제하려 하면 정확히 일치가 665->669(+4,
  86.7%->87.2%)로 미미하게만 오르는 동안 오답이 28->40~57(거의 2배)로 훨씬 크게
  늘어남 - "확신도만 낮았지 사실 맞았던" 극소수 사례(대전89아6993 등 4건)와
  "확신도도 낮고 실제로도 틀린" 다수 사례(경남14노7607 등)가 정규화 후에도 거의
  안 갈라짐(정규화가 1/T 지수라 원래 확신도가 아무리 작아도 거의 다 0.95~0.99대로
  뭉쳐버려서 순위 변별력이 오히려 떨어짐). 즉 "왜 2줄 통과율이 낮은가"라는 질문의
  답은 맞았지만(T가 2배라 확신도가 구조적으로 낮게 나옴), 그게 "그러면 임계값을
  고치면 된다"로 이어지진 않음 - 저확신도 영역 자체가 실제로 대부분 진짜 오답이라
  거를 방법이 없는 것으로 최종 확인됨.
- **결론**: `ctc_beam_search_decode`/`ocr_plate`의 실제 확신도 계산·임계값(0.5)은
  그대로 유지함(변경 없음) - 진단 함수(`estimate_timesteps`/`normalized_confidence`)와
  CSV 진단 컬럼은 향후 참고용으로 코드에 남겨두되, 프로덕션 로직에는 반영 안 함.
- **다음으로 시도해볼 만한 방향(진단만 완료, 아직 미착수)**: 2줄 실패 48건을
  검출확신도(YOLO)별로 나눠보면 뚜렷한 상관관계가 있음 - 검출확신도 0.95 이상은
  정확히 일치 99.1%(111/112)인데, 0.85 미만으로 떨어지면 8.3~33.3%까지 폭락함
  (해당 구간 표본은 20장으로 적지만 방향성이 매우 뚜렷함). 확신도 계산 문제가
  아니라 YOLO 검출 자체가 애매한 사진(원거리/각도/저조도)에서 크롭 품질이
  나빠지는 게 근본 원인일 가능성이 높음 - 다음 세션에서 이 저확신도 구간 크롭을
  직접 눈으로 확인해서(unwrap_two_line 결과물이 실제로 어떻게 깨지는지) 개선
  여지가 있는지 살펴볼 필요 있음.
